# 증권사 리포트 수집·분석 Agent 설계서

> **문서 목적**: Claude Code에서 구현 시 참조할 계획서  
> **작성 기준**: Telegram MCP 계정 접속 / 키워드 검색 / 최근 1년 / 모든 파일 형식 수집  
> **산출물 포맷**: 수집 파일 묶음 + 마크다운(.md) + Word 문서(.docx)  
> **출력 폴더**: 독립 프로젝트 폴더 (DART agent와 분리)

---

## 1. 작업 컨텍스트 문서

### 1.1 배경 및 목적

주식 분석 멀티에이전트 시스템의 **두 번째 서브에이전트**로, 텔레그램에 유통되는 증권사 리포트를 자동 수집하고 긍정/부정 의견을 구조화하여 Best Case · Worst Case 시나리오를 도출한다. 정성적 시장 시각(Sell-side View)을 정량화하여 이후 종합 리포트 에이전트의 입력으로 제공한다.

**이 에이전트가 답하는 핵심 질문:**
- 증권가는 지금 이 기업을 어떻게 보고 있는가? (투자의견 분포)
- 애널리스트들이 공통적으로 지목하는 기회 요인과 위험 요인은 무엇인가?
- 낙관 시나리오(Best Case)와 비관 시나리오(Worst Case)에서 예상 주가·실적 범위는?

### 1.2 입출력 정의

| 구분 | 항목 | 설명 |
|------|------|------|
| **입력** | 기업명 (필수) | 텔레그램 검색 키워드로 사용 (예: 삼성전자) |
| **입력** | 종목코드 (선택) | 보조 검색 키워드로 추가 사용 (예: 005930) |
| **입력** | 수집 기간 (선택) | 미입력 시 최근 1년 자동 적용 |
| **출력** | 출력 폴더 | `./{날짜}_{기업명}_telegram/` (없으면 자동 생성) |
| **출력** | 수집 원본 파일 | `./{날짜}_{기업명}_telegram/raw_reports/` 하위 전체 |
| **출력** | 수집 메타데이터 JSON | `./{날짜}_{기업명}_telegram/collection_meta_{날짜}_{기업명}.json` |
| **출력** | 분석 구조화 데이터 JSON | `./{날짜}_{기업명}_telegram/analysis_{날짜}_{기업명}.json` |
| **출력** | 분석 마크다운 리포트 | `./{날짜}_{기업명}_telegram/report_{날짜}_{기업명}.md` |
| **출력** | 분석 Word 리포트 | `./{날짜}_{기업명}_telegram/report_{날짜}_{기업명}.docx` |

### 1.3 분석 범위

**수집 대상:**
- 텔레그램 내 기업명/종목코드 키워드가 포함된 메시지 첨부파일 (PDF, 이미지, 텍스트)
- 첨부파일 없이 텍스트만 있는 리포트 요약 메시지도 수집
- 수집 기간: 최근 1년 (실행일 기준 365일 이전 ~ 현재)

**분석 5대 추출 항목:**

| 항목 | 추출 내용 |
|------|----------|
| 투자의견 | Buy / Hold / Sell 레이팅, 목표주가, 발행 증권사, 날짜 |
| 핵심 논거 | 긍정적(Bullish) 포인트, 부정적(Bearish) 포인트 |
| 리스크 요인 | 단기/중장기 리스크, 불확실성 요인 |
| 실적 전망 | 매출·영업이익·EPS 추정치, 컨센서스 대비 방향 |
| 시나리오 | Best Case / Worst Case 조건 및 주가·실적 범위 |

### 1.4 주요 제약조건

- Telegram MCP는 **내 계정**으로 접속 → 구독 중인 채널/그룹 내 메시지만 검색 가능
- 비공개 채널 미구독 시 해당 채널 리포트 수집 불가 → 스킵 후 로그 기록
- PDF 텍스트 추출 불가(스캔 이미지 PDF) 시 → OCR 시도, 실패 시 파일명만 메타데이터로 기록
- 동일 리포트 중복 수집 가능 → 파일 해시 기반 중복 제거
- 텔레그램 API 레이트 리밋 → 요청 간 딜레이 적용 (스크립트 내 설정)
- 리포트 내 수치(목표주가 등)는 LLM이 직접 계산하지 않고 원문에서 추출만 수행

### 1.5 용어 정의

| 용어 | 정의 |
|------|------|
| Telegram MCP | Claude Code에서 텔레그램 계정을 제어하는 MCP 서버 |
| Sell-side | 증권사 리서치 부서 (기관/개인에게 리포트 제공하는 측) |
| 투자의견 | Buy(매수) / Hold(중립) / Sell(매도) 레이팅 |
| 목표주가 (TP) | 애널리스트가 제시하는 12개월 목표 주가 |
| 컨센서스 | 다수 증권사 추정치의 평균값 |
| Best Case | 긍정 시나리오 — 주요 기회 요인이 모두 실현되는 경우 |
| Worst Case | 비관 시나리오 — 주요 리스크 요인이 모두 현실화되는 경우 |

## 2. 워크플로우 정의

### 2.1 전체 흐름

```
[입력: 기업명 + 종목코드(선택)]
        │
        ▼
[Step 0] 출력 폴더 생성
   ./{날짜}_{기업명}_telegram/ 폴더 및 하위 구조 생성
        │
        ▼
[Step 1] 텔레그램 메시지 검색 및 수집
   telegram-mcp: 기업명/종목코드 키워드로 메시지 검색 (최근 1년)
   → 첨부파일 다운로드 + 텍스트 메시지 저장
        │
        ▼ (수집 건수 확인)
[Step 2] 파일 정리 및 중복 제거
   스크립트: 해시 기반 중복 제거, 파일명 정규화, 메타데이터 JSON 생성
        │
        ▼
[Step 3] 텍스트 추출
   스크립트: PDF 텍스트 추출 (pdfplumber) / 이미지 OCR (pytesseract)
   → 각 리포트별 추출 텍스트를 개별 .txt로 저장
        │
        ▼
[Step 4] LLM 구조화 분석 (리포트별)
   에이전트 직접 수행: 각 리포트에서 5대 항목 추출 → JSON 누적
        │
        ▼
[Step 5] LLM 종합 분석
   에이전트 직접 수행: 전체 리포트 교차 분석
   → 긍정/부정 논거 통합, 투자의견 분포, Best/Worst Case 시나리오 작성
        │
        ▼
[Step 6] 문서 생성
   스크립트: 분석 결과 → md + docx 생성
        │
        ▼
[출력: ./{날짜}_{기업명}_telegram/ 내 전체 산출물]
```

### 2.2 단계별 상세 정의

---

#### Step 0: 출력 폴더 생성

**처리 주체:** 스크립트 (`setup_dirs.py`)

**생성 폴더 구조:**
```
./{날짜}_{기업명}_telegram/
  ├── /raw_reports/        # 수집 원본 파일 (PDF, 이미지, 텍스트)
  ├── /extracted_text/     # 파일별 추출 텍스트 (.txt)
  └── /output/             # 분석 결과 산출물
```

**성공 기준:** 폴더 3개 모두 생성 확인  
**실패 처리:** 권한 오류 시 에스컬레이션 (경로 확인 요청)

---

#### Step 1: 텔레그램 메시지 검색 및 수집

**처리 주체:** telegram-mcp (도구 호출) + 스크립트 (`collect_messages.py`)

**수행 작업:**
- 검색 키워드: `기업명`, `종목코드` (각각 독립 검색 후 합산)
- 검색 범위: 접속 계정이 구독 중인 전체 채널/그룹/DM
- 기간 필터: 실행일로부터 365일 이전 ~ 현재
- 메시지 유형별 처리:
  - 첨부파일(PDF/이미지) → `raw_reports/`에 다운로드
  - 텍스트 전용 메시지 → `raw_reports/{날짜}_text_{index}.txt`로 저장
- 수집 메타데이터 기록: 채널명, 메시지ID, 날짜, 파일명, 파일크기

**분기조건:**
```
수집 결과 = 0건?
  ├─ YES → 에스컬레이션 (키워드 확인 또는 구독 채널 확인 요청)
  └─ NO  → Step 2 진행

첨부파일 다운로드 실패 (단건)?
  ├─ 재시도 2회
  └─ 실패 시 → 메타데이터만 기록 후 스킵
```

**성공 기준:**
- 최소 1건 이상 수집
- 메타데이터 JSON에 수집 건수 기록

**실패 처리:**
- telegram-mcp 연결 오류 → 자동 재시도 3회 (60초 간격) → 에스컬레이션
- 레이트 리밋 감지 → 스크립트 내 자동 대기 후 재개

---

#### Step 2: 파일 정리 및 중복 제거

**처리 주체:** 스크립트 (`deduplicate.py`)

**수행 작업:**
- 파일별 MD5 해시 계산 → 동일 해시 파일 제거 (가장 오래된 날짜 기준 1개 유지)
- 파일명 정규화: `{날짜}_{채널명}_{원본파일명}` 형식으로 rename
- `collection_meta_{날짜}_{기업명}.json` 생성:
  - 총 수집 건수, 중복 제거 건수, 채널별 수집 분포, 파일 형식별 건수
  - 각 파일의 메타데이터 배열 (파일명, 채널, 날짜, 해시, 추출가능여부)

**성공 기준:**
- 메타데이터 JSON 생성 완료
- 중복 제거 후 최소 1건 잔존

**실패 처리:** 중복 제거 후 0건 → 에스컬레이션 (모두 중복이면 검색 기간 확인 요청)

---

#### Step 3: 텍스트 추출

**처리 주체:** 스크립트 (`extract_text.py`)

**파일 유형별 처리:**

| 파일 유형 | 추출 방법 | 실패 시 |
|----------|----------|--------|
| PDF (텍스트 레이어 있음) | `pdfplumber` 텍스트 추출 | OCR 시도 |
| PDF (스캔 이미지) | `pytesseract` OCR (한국어 언어팩) | 메타데이터만 기록, 스킵 |
| 이미지 (JPG/PNG) | `pytesseract` OCR | 메타데이터만 기록, 스킵 |
| 텍스트 (.txt) | 직접 읽기 | — |

**출력:** `extracted_text/{파일명}.txt` (파일당 1개)  
**추출 품질 플래그:** 텍스트 길이 < 200자이면 `low_quality` 플래그 → LLM 분석 시 신뢰도 낮음으로 처리

**성공 기준:** 전체 파일 중 50% 이상 텍스트 추출 성공  
**실패 처리:** 50% 미만 추출 시 → 에스컬레이션 (OCR 환경 확인 요청), 추출된 파일만으로 분석 계속 진행

---

#### Step 4: LLM 구조화 분석 (리포트별)

**처리 주체:** 에이전트 직접 수행 (LLM 판단 영역)

**처리 단위:** 추출된 텍스트 파일 1개 = 리포트 1건  
**처리 방식:** 파일 순서대로 순차 처리, 결과를 `analysis_{날짜}_{기업명}.json`에 누적

**각 리포트에서 추출할 구조화 데이터:**

```
{
  "source_file": "파일명",
  "channel": "채널명",
  "report_date": "YYYY-MM-DD",
  "securities_firm": "증권사명 (추출 가능 시)",
  "analyst": "애널리스트명 (추출 가능 시)",
  "investment_opinion": "Buy | Hold | Sell | 명시없음",
  "target_price": 숫자 또는 null,
  "current_price_at_report": 숫자 또는 null,
  "bullish_points": ["포인트1", "포인트2", ...],
  "bearish_points": ["포인트1", "포인트2", ...],
  "risk_factors": ["리스크1", "리스크2", ...],
  "earnings_estimates": {
    "revenue": {"value": 숫자, "unit": "억원|조원", "period": "YYYY"},
    "operating_profit": {"value": 숫자, "unit": "억원|조원", "period": "YYYY"},
    "eps": {"value": 숫자, "period": "YYYY"}
  },
  "key_catalysts": ["촉매1", "촉매2", ...],
  "quality_flag": "normal | low_quality | ocr_only",
  "confidence": "high | medium | low"
}
```

**LLM 판단 지침:**
- 명시적으로 적힌 수치만 추출 (추론/계산 금지)
- 투자의견이 명시 없는 경우 → `"명시없음"` 기록 (임의 판단 금지)
- `low_quality` 플래그 파일은 추출 항목이 일부 null이어도 허용
- 리포트 텍스트가 해당 기업과 무관하다고 판단 시 → `"irrelevant": true` 표기

**성공 기준 (LLM 자기 검증):**
- 필수 필드(`source_file`, `report_date`, `bullish_points`, `bearish_points`) 존재
- `investment_opinion` 필드 반드시 포함 (null 불허, `"명시없음"` 허용)
- 수치 필드에 문자열 혼입 없음

**실패 처리:**
- 자기 검증 실패 → 해당 리포트 재분석 1회
- 2회 연속 실패 → `"parse_failed": true` 기록 후 스킵, 다음 파일 진행

---

#### Step 5: LLM 종합 분석

**처리 주체:** 에이전트 직접 수행 (LLM 판단 영역)

**입력:** Step 4에서 누적된 `analysis_{날짜}_{기업명}.json` 전체

**분석 구조:**

```
1. 수집 개요
   - 총 수집 리포트 수, 유효 분석 건수, 기간 범위
   - 참여 증권사 목록 및 각 사별 리포트 수

2. 투자의견 분포 분석
   - Buy / Hold / Sell 건수 및 비율
   - 목표주가 범위 (최소 ~ 최대 ~ 평균)
   - 시계열 추이: 최근 6개월 vs 그 이전 의견 변화 방향

3. 긍정 논거 통합 (Bullish Case)
   - 공통적으로 언급된 긍정 포인트 (언급 빈도 포함)
   - 증권사별 차별화된 긍정 시각
   - 핵심 촉매(Catalyst) 목록

4. 부정 논거 통합 (Bearish Case)
   - 공통적으로 언급된 부정 포인트 (언급 빈도 포함)
   - 증권사별 차별화된 우려 시각
   - 핵심 리스크 목록

5. 실적 전망 컨센서스
   - 매출 / 영업이익 / EPS 추정치 범위 (최소 ~ 최대 ~ 평균)
   - 가장 낙관적인 증권사 vs 가장 보수적인 증권사 비교
   - 추정치 분산 수준 (의견 수렴 vs 분산)

6. Best Case 시나리오
   - 전제 조건: 어떤 긍정 요인이 동시에 실현되어야 하는가
   - 기대 주가 범위 (최고 목표주가 기준)
   - 기대 실적 범위 (가장 낙관적 추정치 기준)
   - 실현 가능성에 대한 에이전트 평가

7. Worst Case 시나리오
   - 전제 조건: 어떤 리스크 요인이 동시에 현실화되어야 하는가
   - 예상 주가 범위 (가장 보수적 목표주가 또는 하단 추정)
   - 예상 실적 범위 (가장 보수적 추정치 기준)
   - 현실화 가능성에 대한 에이전트 평가

8. 종합 시각 요약
   - 증권가 전반의 온도 (매우 긍정 / 긍정 / 중립 / 부정 / 매우 부정)
   - 의견 수렴도 (컨센서스 강도)
   - 가장 최근 리포트 기준 방향성 변화 여부
```

**성공 기준 (LLM 자기 검증):**
- 8개 섹션 모두 서술 존재
- Best/Worst Case에 각각 전제조건·주가범위·실적범위 3요소 포함
- 수치 인용 시 출처 리포트 명시 (날짜 + 증권사)
- 주관적 단언 금지 → 근거 데이터 없는 전망은 작성 불가

**실패 처리:**
- 자기 검증 실패 → 해당 섹션 재작성 최대 1회
- 유효 리포트 수 < 3건 → 분석 신뢰도 낮음 경고 문구 삽입 후 진행

---

#### Step 6: 문서 생성

**처리 주체:** 스크립트 (`generate_report.py`)

**마크다운 리포트 (.md):**
- Step 5 분석 전체 텍스트 구조화
- 투자의견 분포 텍스트 테이블 포함
- `output/report_{날짜}_{기업명}.md` 저장

**Word 리포트 (.docx):**
- `docx` npm 라이브러리 사용
- 표지 (기업명, 분석일자, 수집 리포트 수, 기간)
- 목차 자동 생성
- 투자의견 분포 테이블 (`Table` 컴포넌트)
- Best/Worst Case 섹션은 시각적으로 구분되는 박스 스타일 적용
- `output/report_{날짜}_{기업명}.docx` 저장

**성공 기준:**
- 두 파일 모두 존재
- docx 유효성 검증 통과 (`validate.py`)

**실패 처리:**
- docx 생성 실패 → md만 최종 산출, 오류 로그 기록

| 문서 포매팅 | 스크립트 | 파일 생성 I/O |

### 3.3 에이전트 구조

**단일 에이전트** 구조 채택

**근거:** 수집 → 추출 → 분석의 흐름이 순차적이며, 리포트별 분석(Step 4) 결과가 종합 분석(Step 5)의 직접 입력이 되므로 컨텍스트 연속성이 중요. 리포트 수가 많아질 경우(30건 이상) 컨텍스트 윈도우 초과 가능성이 있으므로 Step 4에서 JSON 중간 저장 후 Step 5에서 파일로 재로드하는 패턴 적용.

### 3.4 스킬 파일 목록 및 역할

| 스킬명 | 역할 | 트리거 조건 |
|--------|------|-----------|
| `telegram-collector` | MCP 호출, 메시지 검색, 파일 다운로드, 중복 제거 | 워크플로우 시작 시 |
| `text-extractor` | PDF/이미지에서 텍스트 추출, 품질 플래그 부여 | 수집 완료 직후 |
| `report-analyzer` | 리포트별 구조화 추출 및 종합 분석 지침 제공 | 텍스트 추출 완료 직후 (LLM 참조용) |
| `report-builder` | 출력 폴더 생성 + md/docx 문서 생성 | LLM 종합 분석 완료 직후 |

## 4. 설계 결정 근거 (주요 판단 기록)

| 결정 항목 | 선택 | 근거 |
|----------|------|------|
| 단일 vs 멀티 에이전트 | 단일 에이전트 | 수집→분석 컨텍스트 연속성 필요, 리포트 수가 많으면 JSON 파일 재로드로 대응 |
| 폴더 분리 방식 | `_telegram` 접미사 독립 폴더 | DART agent와 실행 시점이 다를 수 있고, 단독 실행도 가능해야 함 |
| 수치 추출 방식 | 원문 그대로 추출 (계산 금지) | 오계산 방지, 출처 추적 가능성 확보 |
| 투자의견 처리 | 명시 없으면 "명시없음" (임의 판단 금지) | 분석 신뢰도 유지, 편향 방지 |
| 중복 제거 기준 | MD5 해시 | 파일명이 달라도 동일 리포트 제거 가능 |
| Best/Worst Case 도출 | 실제 추출 데이터 기반 | 수집된 리포트에 없는 전망 작성 금지 원칙 유지 |
| Step 4→5 데이터 전달 | JSON 파일 재로드 | 리포트 수 증가 시 컨텍스트 윈도우 초과 방지 |
